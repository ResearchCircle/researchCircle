# V2 corrected specification

Date: 2026-10-29. Status: authoritative implementation design; implementation and hardware acceptance are outstanding.

## 1. Authority, scope and claims

This document replaces the implementation instructions in chapters 01–15 and the old JSON briefs. Read [the audit](../16-v2-critical-review-and-revised-plan.md) for evidence and [the team plan](../18-four-person-delivery-plan.md) for delivery. When code disagrees with this specification, code is incomplete; passing existing tests does not override the specification. This revision closes the identified design defects by choosing concrete contracts, withdrawing unsupportable promises and assigning acceptance gates. It does not claim that every possible vulnerability has been discovered.

Build in **this repository**, using the existing `packages/`, `services/`, and `frontend/` roots. Do not create a second `tigerexchange/` project. Existing `src/` is reusable legacy material, not a trusted v2 backend. Port selected algorithms behind the new interfaces; never mount legacy routes with confidential data or allow cloud fallback.

**V2 pilot includes:** authenticated public discovery, researcher shortlist, verified opportunity/manual import, pursuit tracking, direct proposal invitations, real-time co-editing, confidential local drafting from explicitly approved documents, cited output, Markdown/DOCX export, durable outcomes and consent-controlled public writeback. Export and manual submission recording do not submit applications to funder portals.

**Deferred extensions:** persistent confidential vector/BM25 indexes, instantaneous physical/backup crypto-erasure, inherited group roles, comments/tracked changes, fuzzy identity merges, federation, outcome-based ranking in production, and automatic confidential-to-public publication. These are not hidden requirements in the pilot definition of done. Private grounding remains available through authorized selection and transient processing of source documents. Each deferred extension needs its own reviewed design and acceptance evidence before enabling it; old chapters are not approved implementations of those extensions.

Assumed operating envelope: 3 groups, 20 registered users, 10 simultaneous editing connections across at most 5 open proposals, 100k public chunks, 10 selected sources per draft, 2 MiB CRDT document state. These are **initial acceptance targets**, not measured capacity claims. Anurag may lower them based on Orin measurements; increases require rerunning capacity and abuse tests.

## 2. Threat model and trust boundary

Defend against malicious authenticated users, forged resource/tenant IDs, stale sessions, accidental cross-tenant access, hostile uploaded/imported text, duplicate/reordered messages, service crashes, disk-full conditions and network interruption. The host operator, migration role, application executable and key service are trusted. This is not protection against a hostile root operator or compromised application process with access to plaintext. Do not describe mounted encryption, Python import rules or RLS as physical tenant isolation.

All browser/API access is TLS, same-origin, authenticated. Database and model endpoints bind to private interfaces and are unreachable from browsers. Runtime network egress is denied for confidential-serving processes; public ingest has a separate allowlisted fetcher. No real private documents, keys or raw prompts enter source control, CI fixtures, issue reports or teammates' development environments.

## 3. Identity, tenant ownership and direct roles

A tenant is a research group. A user has a stable local UUID and may belong to multiple groups. Proposals have exactly one immutable owner tenant; invited guests retain their own user identity. No tenant transfer in the pilot. Public researcher identities are separate from login accounts; claiming a profile requires owner verification, not a name match.

Use local invite-only accounts for the pilot, Argon2id password hashes, opaque server-side sessions, Secure/HttpOnly/SameSite=Lax cookies, CSRF tokens for mutations, strict origin checks on websockets, 8-hour absolute and 30-minute idle session expiry. Rotate sessions on login/password reset and revoke them on account disable. Rate-limit login to 5 failed attempts per account/IP per 15 minutes; return generic errors. Anurag provisions the first administrator and verifies account recovery out of band. No self-service tenant creation or automatic email delivery is required. Invitation links are manually shared by the inviter, expire after 48 hours, are single-use and bound to an intended verified account/email; only token hashes are stored. Require TOTP for administrative accounts before real confidential data.

Proposal roles: `owner`, `editor`, `viewer`. Owner can invite/revoke, approve sources, export and delete; editor can read/edit and request drafts from the approved set; viewer can read only. One owner user at creation; ownership reassignment is out of pilot scope. Group membership alone does not confer proposal access. No inherited role cascade or highest-permission merge. A unique `(proposal_id, user_id)` membership row has an explicit role, active state and monotonically increasing epoch.

Capabilities and tier are derived server-side from authenticated identity, stored resources and the action registry. Request JSON cannot grant capability, choose effective tenant context, downgrade tier, set owner identity or supply an authorization decision. Unauthorized object IDs return the same 404 as absent IDs; validation errors must not reveal another tenant's existence.

## 4. Database boundary and permissions

PostgreSQL 16, pgvector for the public corpus, SQLAlchemy/Alembic migrations. Use native Postgres full-text search initially for the lexical leg; call it FTS, not BM25. Optional BM25 is a later measured adapter upgrade and is not on the critical path. No confidential indexes or tenant partitions in the pilot. Use direct asyncpg/SQLAlchemy pooling initially; PgBouncer is deferred until its transaction-mode isolation tests pass.

Every tenant table uses FORCE RLS with an explicit reviewed permissive policy **and** a restrictive tenant boundary. Example policy shape (migration templates substitute identifiers, never user strings):

```sql
ALTER TABLE tex.example ENABLE ROW LEVEL SECURITY;
ALTER TABLE tex.example FORCE ROW LEVEL SECURITY;
CREATE POLICY app_access ON tex.example AS PERMISSIVE FOR ALL TO tex_app
  USING (true) WITH CHECK (true);
CREATE POLICY tenant_boundary ON tex.example AS RESTRICTIVE FOR ALL TO tex_app
  USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
```

The policy does not itself grant SQL privileges. Roles: `tex_migrate` owns schema and cannot be used by serving processes; `tex_app` gets only required business-table DML; `tex_ingest` writes only public staging/corpus; `tex_events` reads/claims pending outbox rows and writes designated receipts; `tex_audit` inserts audit records; key material is accessible only through the key service role. The role owning a business transaction also receives narrowly scoped INSERT on its tenant audit/tombstone/outbox records so these writes commit atomically; it cannot UPDATE/DELETE them. `tex_audit` is for standalone append-only events, not a second connection inside a business transaction. None of the runtime roles is superuser/BYPASSRLS or can SET ROLE to a stronger role. No blanket default DML grants. Grant audit/tombstone writers INSERT/SELECT as required, never UPDATE/DELETE; a separately audited retention job owns audit expiry; lifecycle tombstones do not expire. Public-corpus writes are not granted to ordinary feature handlers. Apply the tenant boundary explicitly to every role accessing a tenant table, including `tex_events`; policies for `tex_app` alone do not authorize workers. A minimal queue directory exposes only event_id/tenant_id/status/due_at/lease fields to the scheduler; payload access and effects occur in a tenant-scoped transaction. Workers rederive authorized effects from the durable event and current lifecycle/publication state, never from a client-supplied actor or tenant.

RLS is defense against tenant-context mistakes, not arbitrary hostile SQL in a trusted process. A narrow resource-directory adapter can map an opaque proposal ID to owner tenant without returning titles/content; the broker then sets owner context transaction-locally with bound `set_config(..., true)` and validates the **actor's direct membership** before any content operation. Guests never receive owner-tenant credentials or general owner-corpus query capability. Runtime handlers have no raw SQL connections; broker adapters own access. No SECURITY DEFINER bypass for guests.

Schema source of truth is executable migrations, not copied Markdown DDL. Tables must include composite tenant/object foreign keys for tenant-owned relationships, state CHECKs, uniqueness for idempotency keys and UTC timestamps. UUID/enum/validation definitions come from contracts. Audit/analytics payloads contain IDs, action, result and timestamps only; sensitive titles, questions, outcomes detail, proposal content, extracted text and source metadata are encrypted payloads.

## 5. Authorization, revocation and operation ordering

All object read/write/export/source-read/generation deliveries go through the broker. Its order is authentication → action/capability → stored tier/audience → direct role → lifecycle/authorization generation → operation. Any dependency error denies the confidential operation. No cached positive authorization survives an epoch change; no client or background job can bypass the broker.

Use Postgres **transaction-scoped shared/exclusive advisory locks** as the cross-process document fence. The lock key is a deterministic signed 64-bit digest of `(resource_kind, owner_tenant_id, resource_id)`; a collision only adds serialization, never shares authorization. Every operation first takes the owner tenant's shared lifecycle lock, then all proposal/source locks in sorted key order. Tenant offboarding takes the tenant exclusive lock and marks it inactive, preventing new resource creation and operation admission before per-document cleanup. Source withdrawal or disclosure-permission change takes the source exclusive lock; every source-based delivery takes its shared lock through validation and enqueue. For cross-owner references, acquire all tenant locks in sorted order first; pilot confidential source selection is restricted to the proposal owner tenant. Use READ COMMITTED and read authorization in a statement **after** acquiring the lock so a transaction waiting on revocation does not use a stale snapshot.

- Reads, CRDT updates and each bounded outbound stream/broadcast batch take a shared lock, recheck actor membership, document lifecycle and epochs, perform admission/durable work, and enqueue bytes to the transport before releasing the lock. Do not authorize once and defer the actual enqueue to an unchecked callback.
- A revoke takes the exclusive lock, marks the membership inactive, increments its epoch and the proposal audience epoch, appends the immutable tombstone and audit/outbox records in **one transaction**, then commits with `synchronous_commit=on` and `fsync=on`. No CHECKPOINT and no `committed` boolean.
- Source withdrawal/deletion uses the same ordering and durable acknowledgement as membership revocation. The successful revocation response is sent only after the independent revocation recovery journal in §11 is durable. All subsequent admissions re-read the inactive membership. Socket close notifications are cleanup, not authority. Generation and export results computed earlier are discarded when their captured epoch is stale.
- A 5-second operation fence timeout fails closed with a retryable 503; revoke remains pending/uncertain, never falsely successful. A committed revoke stays enforced even if journal write or response fails; retry by idempotency key finishes acknowledgement. Multi-recipient broadcast validates each recipient under the document fence.

**Guarantee:** after successful revocation acknowledgement, no new server-authorized disclosure or mutation for the removed principal is admitted. Already-enqueued network bytes may arrive later; downloaded copies cannot be recalled. This is deliberately not a claim of instantaneous retraction. Account/session disabling checks apply at every admission too. If Postgres is unreachable, sockets stop accepting and broadcasting updates; local room caches cannot authorize.

## 6. Lifecycle, deletion and cryptography

Separate API operations: `revoke_member`, `delete_document`, `offboard_tenant`. Revoking a member never destroys keys. Documents transition PROVISIONING → ACTIVE → DELETED; grants ACTIVE → REVOKED. Tombstones remain in the recovery journal for the lifetime of the deployment. Document IDs are never reused; deleted documents cannot be restored by ingestion or CRDT clients. A future explicit restore must create a new document ID after a separate authorization decision.

Creation is an idempotent provisioning workflow: commit a non-readable PROVISIONING row with an operation UUID; the key service provisions its key and initial encrypted state by that UUID; commit the encrypted state/reference and switch to ACTIVE atomically. Key-service provisioning RPC is separate from ordinary decrypt and accepts only the authenticated broker, matching operation UUID and PROVISIONING resource. No reads, invitations, model jobs or exports can use a PROVISIONING resource. Retry resumes the same key/document; never allocate a second key silently. A crash at each step leaves an inaccessible retryable record; an operator-visible cleanup task tombstones abandoned provisioning after 24 hours and removes its orphaned key/ciphertext.

Each proposal/source document has its own random 256-bit data key; wrapped by a tenant key under the box master. AES-256-GCM via `cryptography` encrypts all persisted confidential content, CRDT updates/snapshots, exports stored temporarily, source text and generated private text. Nonce uniqueness is mandatory: random 96-bit nonce with a database uniqueness constraint on `(key_id, nonce)` and retry on collision. Canonical AAD binds tenant, document, content kind, schema version, sequence and key ID. Verify AAD before parsing. Never log plaintext or keys. Small non-content routing metadata is not claimed to be secret from the trusted operator.

The Anurag-owned `services/key_service/` process owns master/key custody and serves encrypt/decrypt/wrap operations over a Unix-domain socket restricted by OS user/group to the broker and room services. No browser/worker/model service can call it directly. Callers must hold the operation fence; the service validates authenticated peer identity, resource/key association, active tenant/document state and expected AAD fields. Locked, unavailable or timed-out (2-second deadline) key service means DENY/no plaintext fallback. Health exposes only locked/ready/error, never key metadata. Dev uses the same protocol with local test keys. The recovery journal uses a separate box recovery key independent of document/tenant keys, included in the encrypted offline recovery package.

Default master unlock is an operator-entered passphrase using Argon2id (initial parameters 64 MiB, 3 iterations, parallelism 4, 16-byte random salt; record format/parameters and benchmark). Derive a wrapping key from its output with domain separation; do not apply SP 800-108 directly to a password. Master/key material stays in the key-service process; production startup remains locked until operator unlock. fTPM is optional later hardening, not a release dependency. Require an encrypted offline recovery package under a separately stored recovery secret; test recovery and rotation without placing secrets in reports.

Deleting X atomically blocks X, records its tombstone and schedules removal of X's current wrapped key, ciphertext and derivatives; invalidate X's room/source/job caches under the fence. Y remains readable. Tenant offboarding performs this for its entire owned corpus and removes its access to other owners' proposals without deleting those proposals. Reconcile references and cancel running jobs idempotently.

**Retention contract:** logical access denial is immediate under §5. Live-data purge completes within 24 hours, or an operator alert marks deletion pending. Encrypted recovery backups are retained for at most 30 days; old recoverable keys may exist there. No claim of immediate forensic erasure or all-backup crypto-shredding. Retention expiry takes priority over recovery coverage: delete expired backup sets/keys at the deadline even if a new backup failed. Alert before expiry and on any retention violation; if recovery coverage is no longer safe, block new confidential writes until a fresh backup is verified. Never silently extend retention to protect recoverability. The UI/operator report records any resulting recovery limitation and pending live purge. Restore replays the current tombstone journal before serving and re-purges deleted content. Tenant consent UI states this policy before confidential upload.

Disable application/core dumps and confidential request-body/access logging. Use encrypted swap or disable swap; confidential extraction is bounded in memory, never an ordinary disk temp directory. Audit temp files, crash dumps, model logging and exports with planted canary text. OS/GPU memory zeroization is not guaranteed by Python or process serialization and is not promised.

## 7. Grounding, audience and public publication

Sources are immutable versions. A proposal owner explicitly approves each confidential source version **for that proposal's audience**, and must also hold `may_disclose` on the source as its uploader or an explicitly designated source custodian. Read permission alone never grants disclosure authority. Pilot confidential sources must belong to the proposal owner tenant; other-tenant private sources are rejected. Source custody/disclosure changes take the source lifecycle fence; an editor cannot pull arbitrary owner-private records. An approval binds source version/hash, destination proposal and audience epoch. The consent text explains that generated text/citations may reveal the approved source. Adding a member or expanding a role's read access requires owner confirmation that existing proposal content and its source approvals may be disclosed to the expanded audience; approvals are rebound to the new epoch in the same transaction. Without confirmation, the invitation is not activated. Revoking membership invalidates in-flight jobs; unchanged sources can be reapproved for the smaller audience.

Before generation, the broker validates every selected source against the actor's proposal role, the approval issuer's continuing source disclosure authority and the destination audience. An editor or guest editor may use an existing valid approval without personally having `may_disclose`; they cannot issue/expand that approval or directly browse the private source corpus. Test this legitimate drafting path alongside denial of unapproved sources. Jobs capture each source authorization generation. Every output batch holds both source and destination shared fences while rechecking generations and enqueuing; source withdrawal cannot race between validation and disclosure. Invitation acceptance checks its owner-confirmed expected audience epoch; a changed audience requires owner reconfirmation rather than silently broadening earlier source approval. Public retrieval and approved confidential text are combined transiently. No owner-only generation is silently inserted in a shared document: the pilot supports generation only for the destination proposal's approved audience. Generated text remains a suggestion until an authorized editor accepts it through a normal versioned document update. Revalidate audience/source/lifecycle at final delivery and acceptance. If a source is withdrawn, stop its future use and mark existing dependent suggestions/documents for owner review; already disclosed text cannot be undisclosed. Provenance links must let an owner locate affected derivatives.

Public publication is a separate owner-approved transition for exact immutable field values/hash. Classifiers may deny or quarantine; they cannot grant publication rights. `PublicProjection` requires tier PUBLIC, positive version, active publication generation, provenance and an explicit public schema with extra fields forbidden. Default visibility is NONE until a trusted public import or owner publication approval. Private/confidential data never belongs to a public projection, even with TENANT scope. Apply this to graph edges, membership, award facts, scores and analytics, not just papers.

Public applier: lock publication state; require ACTIVE, generation equality, valid approval/provenance and strictly increasing content version; apply and record event receipt atomically. Revocation flips ACTIVE to REVOKED and removes public derivatives. No larger content version can clear the tombstone. Re-publication requires an explicit new approval/generation. Alias remapping preserves tombstones and provenance. Positive and negative tests include high-version replay and concurrent publication/revocation.

## 8. Editor and recovery contract

Use pycrdt on the server and a compatible browser Yjs client, exact versions pinned by a serialization compatibility test. One authoritative websocket room process in the pilot; no multi-server room fanout. API and room process share the database fence. Require session authentication and origin checks at connect and authorization at every update/broadcast; reject viewer updates before CRDT application. No offline editing/persistent browser document cache in the pilot.

Each room has a mutation mutex held across candidate construction, server sequence allocation, encryption/commit and live-state application. Snapshot/compaction takes the same mutex. The single room service routes all document mutations, including accepted suggestions, through this path. Acquire room mutex before the sorted database locks consistently; revocation never takes the room mutex while holding database locks. A second room service is prohibited until a separate ownership/fencing design is reviewed.

Each submitted batch has `(document_id, client_id, client_sequence)` idempotency key and base document generation. Validate bounded bytes, CRDT schema and post-apply size using a candidate copy; encrypt and commit the update/sequence before acknowledging saved or broadcasting. If commit succeeds but application/broadcast fails, replay committed updates; if commit fails, discard the candidate. Snapshots every 100 updates or 30 seconds compact only committed prefixes; never delete the update tail before a durable snapshot. Server-generated monotonic sequence determines replay order; snapshot version and AAD must agree.

Saved means committed to the primary disk, not merely echoed by a peer. UI distinguishes pending/saved/offline/failed and displays conflicts for rejected stale lifecycle state. Crash of the server and every browser loses **zero acknowledged edits if the primary disk survives**. Disk-loss RPO is separate (§11). Duplicate batches return their prior sequence. Reconnecting clients reauthenticate and cannot resurrect a deleted document or replay edits after membership revocation.

Limits: 64 KiB incoming update, 2 MiB resulting document, 20 updates/second/connection burst and 5/second sustained (batch client keystrokes), max 10 simultaneous connections. Close malformed/oversized clients without taking down other rooms. Server state is canonical; client awareness/cursor metadata must not contain arbitrary private payloads.

## 9. Model service and resource ownership

One local generator process, one resource coordinator, one queue for **all** generator traffic. Public embedding/reranking use separately typed internal operations in the same resource coordinator, not a fake proposal-drafting request. Public reranking admits at most 50 candidates, 512 tokens/candidate and a 2-second budget; if unavailable, return the public fused ranking marked degraded. Embedding batches are at most 32 texts × 512 tokens and bulk embedding runs only in MAINTENANCE. GPU preprocessing and generation share an exclusive resource lease; pending interactive drafts take priority over public reranking, and each admitted batch finishes or aborts before another GPU operation starts. Tune these targets only with measured evidence. Generator prefix caching is disabled globally with the pinned engine's documented setting; no presumed per-request toggle. Pilot concurrency is 1 with at most 4 waiting jobs, one queued job/user and fair scheduling across tenants. Input max 8192 tokens, output max 512 tokens, maximum run 90 seconds and queue wait 30 seconds. Reject oversized requests before model admission. Timeout/cancel releases capacity only after the backend confirms completion/abort; if uncertain, stop admissions and restart the generator before reuse.

The coordinator is a single runnable service using Postgres job leases and generation fencing; clients cannot reach the generator directly. On coordinator restart, reconcile or terminate all outstanding backend work before accepting jobs. A plain asyncio semaphore in API workers is insufficient. Prefix caching off and serialization reduce sharing; they do not establish process or physical memory isolation.

Embed/rerank/extraction are confidential operations whenever their input is confidential. All use local endpoints, the same destination allowlist and sanitized telemetry. A response flag cannot prove locality; enforce outbound destination before sending. Public import fetchers have no access to key-service/model-private credentials. Generation never executes tools or instructions found in retrieved text. Output is escaped/sanitized and citations resolve to authorized source IDs/versions.

Regimes: SERVE; MAINTENANCE (bulk ingestion/index builds with drafting paused and editor still available); STOPPED/RECOVERING. Outcome bookkeeping needs no GPU or SPECTER2 reload. One coordinator drains generation before maintenance; bounded CPU/I/O jobs allow editor operations. Do not use the historical writeback memory arithmetic as evidence. Anurag records measured board memory/latency/temperature for the exact model artifact, image digest, quantization and context settings. Target peak ≤54 GiB, leaving operating margin; target empty-queue first token p95 ≤5 seconds, draft completion p95 ≤60 seconds for 4k input/512 output. These are go/no-go targets, not guaranteed benchmarks; choose a smaller local model if necessary, never silently use cloud fallback.

## 10. Public data, outcomes and event delivery

Public corpus starts at 100k chunks, bge-m3-compatible 1024-dimensional embeddings behind a versioned embedding interface, native FTS + vector candidates fused by RRF, local reranking when its measured budget permits. One embedding model/version per index; never mix dimensions or silently backfill a different model. Retain a lexical-only public mode when embeddings are unavailable, with a visible degraded-state flag. Confidential drafting never falls back to an unauthorized source/provider.

Start with a checked-in synthetic fixture and one licensed public import format; one OpenAlex adapter and verified manual opportunity import are sufficient for pilot. Record URL/source ID, retrieved_at, license, content hash, source version and normalization version. External schedules/API availability are configuration verified at implementation time. Missing identity anchors create unresolved records; no guessed ORCID or automatic name merge. Opportunity deadlines include timezone and source; unknown eligibility is explicitly unknown. Require user verification of the source call before marking ready to submit.

Uploads: PDF/text only, 10 MiB file limit, 100 pages, maximum 30-second extraction and 512 MiB isolated-worker memory; no executable content, archives, arbitrary URL fetching or document macros. Public fetcher rejects loopback/private/link-local/metadata addresses, revalidates redirects and resolved targets, limits body size/time and uses a source allowlist. Process confidential files in memory; encrypted original and extraction only. Legacy cloud extraction paths must be removed from the v2 dependency path.

Pursuit states: DRAFT → SHORTLISTED → COLLABORATING → SUBMITTED → WON/LOST/WITHDRAWN; withdrawal is allowed before submission too. Unknown outcome remains SUBMITTED, never inferred LOST. Every transition is version-checked and idempotent; award corrections append superseding events rather than overwriting history. Only proposal owner records submission/outcome; editors curate shortlist/edit proposals. Submission needs source deadline/eligibility verification, export confirmation and a user timestamp/reference. Store confidential details encrypted. Public award facts require the publication flow in §7.

Outbox rows are inserted in the same transaction as business changes. Workers claim pending/retry-due rows with `FOR UPDATE SKIP LOCKED`, owner lease and attempt count; never advance a global sequence cursor to imply completion. Effect receipts have unique `(consumer, event_id)` keys and commit atomically with database effects; duplicates are no-ops. Lease expiry allows reclaim; stale workers cannot acknowledge a new holder's lease. External effects use their own idempotency keys; no external email sends in pilot. Retry exponentially up to 8 attempts, then dead-letter with operator-visible replay preserving the original event ID. Corrections rebuild projections deterministically from the outcome ledger, not repeated additive increments.

Outcome ranking weight is zero in production. A separate offline experiment normalizes feature scales, uses time-separated labels, compares to the static baseline and reports career-stage/group coverage. A rank change is not a quality gate. Pilot success: at least two groups complete repeated cross-group editing, experts accept useful shortlists, citations are checked and export/submission workflow is usable. No unsupported competitive exclusivity claims.

## 11. Operations, backup and incident recovery

Runtime: single FastAPI app, one room service, one key service, one coordinator, bounded workers and Postgres, all on Orin. One same-origin reverse proxy serves frontend/API/ws. Docker images and Python/npm locks are exact and tested on ARM64; local development uses the same database major and schema. Dependencies are installed in project environments, not assumed from a developer's global Python. Model endpoints require internal credentials and are never published. No arbitrary browser origins or wildcard credentialed CORS.

Use encrypted daily base backups plus continuous WAL archive to the separate local HDD, with max 15-minute data-loss target after primary disk loss, 30-day retention and a 4-hour restore target. Both RPO/RTO must be measured before pilot release. Copies on the same machine do not cover theft/fire/chassis loss; the pilot explicitly accepts whole-box loss unless an offline external backup is added by the operator. No remote/cloud backup dependency is implied.

Maintain a separate append-only encrypted revocation/deletion journal on the recovery disk. Each record has operation UUID, affected IDs, state/generation, sequence and authenticated chain. One journal writer in the key service serializes append, sequence assignment and fsync; records are deduplicated by operation UUID. A partial unacknowledged tail is truncated only to the last verified complete record during recovery. Sequence continuity checks never silently skip a gap in acknowledged history. A revoke/delete is acknowledged only when its committed state is fsynced there; retry journal delivery idempotently after partial failure. A journal write failure blocks successful acknowledgement and raises an alert while already-committed denial remains in force. Test filesystem permission errors and full disk. The journal contains only committed operations; duplicates are safe. This journal protects acknowledged revocations during a supported primary-disk restore; it does not protect against losing both disks or a malicious operator.

Restore starts RECOVERING, accepts no users, invalidates all sessions, replays the latest journal over the restored database, checks sequence/chain continuity, re-purges deleted content and reconciles jobs/leases. Missing/ambiguous journal means no confidential reopening until operator reconciliation; do not silently accept an older authorization state. Test recovery keys and the journal together. For an ordinary process crash, committed Postgres state is authoritative without restoring an older backup.

Alerts: disk free <20%, failed backup/archive, pending deletion >24h, expired outbox lease/repeated failure, coordinator stuck, failed confidential authorization dependency, memory limit/thermal throttling and journal failure. Metrics have IDs/status/latency only, never body text. Incident procedure: stop confidential admissions, preserve encrypted evidence, revoke affected sessions/keys as scoped, restore verified state, then reopen after Anurag's release check. No destructive migrations at startup; numbered migrations with rollback/forward-repair instructions and pre-upgrade backup.

## 12. Contract and test ownership

The exact shared types and endpoints are defined in the team plan's contract handoff. Commit executable Pydantic schemas/OpenAPI fixtures before parallel implementation. Internal requests include authenticated actor, server-resolved owner, action, source versions, audience epoch and lifecycle generation; public request DTOs omit authority-bearing fields. DTOs reject unknown security fields. Authorization is checked inside the operation transaction, not returned as a reusable boolean to arbitrary callers.

Security changes require Anurag plus one other review; the second reviewer verifies positive functionality as well as attack cases. Anyone may add adversarial tests, but no author can approve weakening their own acceptance gate. Local protocol fakes are allowed only with deterministic synthetic data and an explicit test/development profile; production refuses fake providers. Unit/fake success does not satisfy database, real-browser or Orin acceptance.

## 13. Primary technical references

These establish underlying semantics; the project's protocols still require implementation tests.
